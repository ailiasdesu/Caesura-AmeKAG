# Phase 2: 排查方案设计

## 执行架构

三人并行排查，每天按以下节奏推进：

```
09:00  A/B/C 各自打开飞书 Base，按筛选器过滤自己的域
09:30  各人逐项验证自己的清单，发现问题 → 立即写入飞书 Base
12:00  午休前 A 检查飞书 Base 看板，发现跨模块问题 → 同步
14:00  各自修复自己域里的问题（一个根因 → 一个 commit）
17:00  A 跑全量测试，确认 412 全绿
18:00  A 将当日进展同步到飞书 Base
```

## 并行隔离规则

- **文件锁**：同一文件同一时刻只属于一个人。如果 B 修 Render 时发现需要改 BackendRegistry，先记到飞书，A 来改。
- **不跨域**：每个人只改自己负责的模块。发现别人的模块有问题 → 记飞书 Base，不直接修。
- **回归测试**：每人修完后先跑自己模块的测试，A 合并后跑全量。

## 排查 SOP（每人每天）

1. 打开飞书 Base → 筛选"负责人=自己" → 筛选"状态=待验证"
2. 从列表顶端取一个验证项，按验证方式执行
3. 通过 → 标记 ✅ 通过，写下日期
4. 失败 → 标记 ❌ 失败，写下现象和根因
5. 复现困难 → 标记 🔁 复现困难，记下尝试次数
6. 修复中 → 标记 🔄 修复中
7. 每修完一个 → commit → 跑对应测试 → 更新飞书状态为 ✅

## 飞书 Base 配置增强（Phase 2输出）

当前 Base 有 9 个字段。建议增加以下字段以支持更精细的追踪：

| 新增字段 | 类型 | 用途 |
|----------|------|------|
| 严重程度 | select (P0/P1/P2) | 问题优先级 |
| 排查耗时 | number (分钟) | 统计效率 |
| 关联模块 | text | 跨模块影响记录 |
| 备注 | text | 自由备注 |

## 全流程 demo 验证（D11）

当某人的域全部 ✅ 后，A 启动一次全流程 demo 验证：
- 运行 `build/Debug/CaesuraAmeKAG.exe`
- 执行 `demo/galgame_demo.ks`
- 观察从头到尾无崩溃
- 记录任何异常到飞书 Base
- 目标：连续 5 次无崩溃

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 排查中发现深层架构问题 | 回溯 Phase 2 重新设计，不影响其他排查 |
| 某人进度落后 | A 每天晚上检查，必要时重新分配 |
| 跨模块耦合问题 | 飞书 Base 跨模块影响记录，A 每天汇总裁决 |
| 修复引入新 bug | 每次修复后跑对应测试 + 回归 |
