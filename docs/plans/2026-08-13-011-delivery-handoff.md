## 2. 架构要点（本轮变化）

- **内容寻址翻译键**：`scene .. ":" .. fnv1a(message)`——与 `compiler.hashFile`
  同算法（FNV-1a 32-bit，offset 2166136261/prime 16777619），8-hex。
  键由消息内容决定：场景重排、宏展开、循环内对话都稳定；作者用
  `ks_i18n.lua` 生成模板无需手算键。
- **localize 在 parse_markup 之前**：`[ch]`/`[text]` 的 message 先过
  localize 再进标记解析——译文本身可带 `{color}`/`{size}`/`{b}`/`{i}`；
  backlog/reveal 自动用译文 plain（无额外接线）。
- **markup 白名单**：`expand` 的 gsub 捕获 `{([%w_]+)}` 会撞上
  `{b}`/`{i}`/`{s}`（裸词标记）——白名单原样返回；`{color=...}`/
  `{size=...}` 因含 `=` 天然不匹配；`{/b}` 因含 `/` 天然不匹配。
- **空占位符 = 未翻译**：模板键值为 `""` 时 localize 回退原文（译者
  填空前游戏可玩），非空译文优先于原文。

## 5. 注意事项

- **翻译键稳定性**：键 = scene 文件名（不含路径）+ 消息哈希。改名场景
  文件会使既有译文失联（工具重新生成后 --update 保留旧键不删，可手动
  清理）；消息文本改动 = 新键（旧译文变孤儿，--update 保留）。
- **localize 顺序**：必须在 parse_markup **之前**（译文可带标记）；若
  未来在其它命令接入，遵循同一位置。
- **i18n.load 双形态**：手写语言文件是裸 `{...}` 字面量，工具生成的是
  `return {...}` + 注释头——load 先剥前导注释再按是否含 `return` 决定
  是否补前缀；新写加载路径时勿假设单一形态。
- **Lua 多返回值陷阱**（010 教训延续）：`a and b and f()` 只保留 f 的
  第一个返回值——取 match 多捕获用 if 守卫 + 直接调用。
- **api-stats 计数**：脚本数 73（新增 ks_i18n.lua）、Lua 测试 118
  （新增 test_i18n.lua）——自动生成，勿手改。
